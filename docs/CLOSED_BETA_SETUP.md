# Закрытая версия: доступ и профили

Статус: облачная миграция применена, RLS включён на пяти таблицах, администратор приглашён. Сквозная проверка входа по коду ещё не выполнена. Это не завершённая система биллинга.

## Решение

Рассмотрены общий код доступа, собственная авторизация и Supabase Auth с приглашениями. Выбран Supabase: проверка почты и сессии отделена от продукта. Общий код не даёт личных лимитов; собственные пароли требуют неоправданного сопровождения.

Администратор первоначальной группы: `kulichevserg6@gmail.com`. Роль определяется защищённым приглашением и ID аккаунта, не пользовательскими metadata. Предварительный профиль в localStorage не даёт прав.

## Сценарий входа (2026-10-11)

Рассмотрены пароль, ссылка из письма и одноразовый код. Выбран код: пользователь остаётся в том же окне, не хранит пароль и не попадает случайно в другой браузер. Компромисс — зависимость от доставки писем, срок жизни кода и лимиты Auth. Пересмотреть при устойчивых проблемах доставки.

Первый вход: почта приглашённого Auth-аккаунта → подтверждение кодом → имя и необязательный возраст → Glow. Повторный вход использует сохранённую сессию браузера; в другом браузере нужна новая проверка почты, но заполненный профиль повторно не спрашивается. Очистка данных браузера, выход или истечение сессии требуют нового входа. Обновление токена не должно размонтировать текущий чат.

Наличие email только в `glow_invites` ещё не создаёт Auth-аккаунт: администратор должен отправить приглашение. Клиент не читает whitelist анонимно; окончательный доступ проверяется после подтверждения личности через `glow_access`. Таймер повторной отправки — UX, а не защита: ограничения запросов обеспечиваются Supabase.

## Подготовленная схема

- `glow_invites`: разрешённые email, срок и начальный лимит.
- `glow_access`: роль и блокировка пользователя.
- `glow_profiles`: имя, необязательный возраст, завершение знакомства.
- `glow_credit_ledger`: неизменяемые через клиент начисления/списания с уникальным ID операции.
- `glow_admin_events`: журнал административных операций.

Все таблицы имеют RLS. Пользователь читает собственные данные и обновляет только поля своего профиля. Администратор управляет доступом и начислениями через проверяемые серверные RPC. Роли и операции кредитов недоступны для прямого изменения из браузера.

Сумма кредитов — внутренние единицы тестирования. Новая версия добавляет списание одного кредита за допущенный запрос, ограничения частоты и общей дневной квоты. Миграция 005 применена 13 октября; проверки базы прошли с откатом. Серверный secret добавлен для Preview/next, но сквозная проверка опубликованного API ещё требуется. Это не точная токеновая или денежная тарификация, автоматических возвратов нет. См. [BETA_RELEASE_CHECKLIST.md](BETA_RELEASE_CHECKLIST.md).

## Порядок подключения

1. Применить `supabase/migrations/202610110001_closed_beta.sql` один раз на новом проекте. Миграция создаёт trigger для новых Auth-пользователей; неподготовленное приглашение отклоняется. Существующие аккаунты не импортируются автоматически.
2. В Supabase отключить открытую регистрацию, оставить email и подтверждение email включёнными.
3. Установить Site URL и разрешённые redirect URL, включая `http://localhost:1420` для локального теста. Не использовать wildcard для произвольных доменов.
4. Подключить SMTP. Без него встроенная отправка предназначена только для адресов участников команды Supabase.
5. Настроить Magic link / OTP шаблон с `{{ .Token }}` для кодов. Экран входа рассчитан на код, а стандартный шаблон Supabase содержит ссылку: без изменения шаблона сценарий по коду не готов. На текущем проекте изменение шаблонов требует custom SMTP.
6. Создать приглашение администратору через Authentication → Users → Invite user. Это отправляет письмо: делать только по явному согласию владельца email. Переход по ссылке подтверждает почту; первый вход затем создаёт профиль.
7. Развернуть `glow-invite` и задать `GLOW_ALLOWED_ORIGINS` (список точных origins через запятую). Привилегированный ключ остаётся только в окружении Edge Functions. Функция сама проверяет JWT через Auth и роль через БД до обращения к административному API.
8. Добавить URL проекта и publishable key в локальный `.env.local` / окружение frontend. Не помещать секретный ключ в `VITE_*`.

```dotenv
VITE_SUPABASE_URL=https://your-project.supabase.co
VITE_SUPABASE_PUBLISHABLE_KEY=sb_publishable_your-public-key
VITE_BETA_AUTH_ENABLED=false
```

Флаг выключен до завершения серверного контроля AI и изоляции данных разных аккаунтов. Его можно включить в отдельной локальной тестовой сессии для проверки экрана входа, но нельзя публиковать приложение с одним лишь frontend gate.

## Обязательные проверки перед выпуском

- Аноним не читает таблицы и не вызывает административные RPC.
- Участник не видит другого пользователя, не меняет роль, баланс или блокировку.
- Администратор начисляет кредиты; повтор request ID не начисляет дважды, несовпадающие параметры отклоняются.
- Неприглашённый аккаунт не создаётся; приглашение просрочено/использовано — отклоняется.
- Блокировка проверяется сервером на каждом AI-запросе, включая уже выданные JWT.
- После выхода и смены аккаунта чужие чаты, feedback, память и состояние Artifacts не видны. Текущие глобальные localStorage-ключи ещё требуют разделения по user ID.
- Прямое обращение к `/smartapi` без сессии запрещено. Текущий dev proxy пока не является защищённым beta API.
- Профиль можно изменить/удалить; память отключается независимо от обязательной авторизации. Сейчас экран реализует только первое знакомство: редактирование, передача профиля модели и корректная память ещё требуют подключения.

До этих проверок UI, миграция и сборка не являются доказательством готовности закрытой версии.

## Подготовка Vercel

Существующий проект `glowai` сохраняется; production сейчас связан с `main`, новая версия — с `next`. Не менять production branch до сквозных проверок preview.

Добавлен `/api/ai`: проверка подтверждённой сессии, активного доступа, разрешённой модели и размера запроса; credential остаётся на сервере. Поток передаётся без буферизации всего ответа. `OPENROUTER_API_KEY` — только серверная переменная Vercel, не `VITE_*`. В preview потребуются публичные Supabase URL/key и `VITE_BETA_AUTH_ENABLED=true`.

`GLOW_AI_ENABLED` по умолчанию выключен. Пока не реализованы ограничения частоты/параллельных запросов и бюджет, включать его на публичном сайте нельзя. `max_tokens` ограничивает один ответ, но не суммарные расходы. Маршрут не заменяет биллинг. Dev proxy остаётся отдельным локальным механизмом и не должен выставляться в Интернет.

Не завершено: облачная синхронизация чатов/памяти/настроек, rate limiting, credits, развертывание приглашений, реальная проверка входа, окружение preview и публикация.

## Локальные данные аккаунта

Выбрано пространство хранения по проверенному `user_id`, а не email. Альтернативы: очистка при выходе (теряет историю) и облачная БД (нужны отдельные миграции, конфликты и offline-политика). Подключение рабочего пространства отложено до проверки доступа, чтобы singleton stores не читали данные до выбора аккаунта. Смена аккаунта требует перезагрузки и пересоздания stores. Supabase хранит свою сессию независимо от пользовательских настроек.

Настройки, feedback, инструкции, pairing-состояние и UI Artifacts используют явный scoped storage adapter. Старые общие ключи не удаляются и не импортируются автоматически. В beta браузерные чаты, проекты, Artifacts и память сохраняются в отдельных IndexedDB базах. Записи сериализованы, ошибка сохранения откатывает изменение в памяти. Повторная инициализация разделяет один promise. Для snapshot-базы допускается одна вкладка-писатель; вторую нужно закрыть, чтобы не потерять данные из-за перезаписи snapshot.

Это логическая изоляция в приложении, не шифрование от владельца браузера. При включённом cloud adapter история хранится в Supabase и доступна тому же аккаунту в другом браузере. При выключенном cloud adapter история локальная. Desktop использует отдельные имена SQLite. Legacy-режим без авторизации остаётся прежним, с непостоянной браузерной MemoryDb.

Проверки: `tests/accountStorage.test.mjs` — namespaces, отсутствие доступа до аутентификации, сохранность legacy и запрет смены owner без reload. `tests/storage-browser.html` — реальный IndexedDB/Web Locks, разделение данных, повторное открытие, отказ второму писателю; временные тестовые базы удаляются после проверки.
