# Стабилизация закрытой беты

Статус на 13 октября 2026: миграции 005–006 применены к Supabase. Транзакционная
проверка `tests/betaDatabase.sql` прошла с полным откатом тестовых изменений.
В Vercel подтверждено наличие серверного Secret для Preview/next; значение не
раскрывалось. Проверка опубликованного приложения и реального входа ещё требуется.
Это не отчёт об успешном production E2E.

## Решение о лимитах

Проблема: приглашение нескольких пользователей не должно создавать неограниченный
расход API. Рассмотрены:

1. Только ограничение частоты: просто, но не ограничивает общий объём.
2. Точный учёт токенов/стоимости провайдера: точнее, но требует тарификации,
   резервирования, подтверждённого usage и обработки оборванных потоков.
3. Консервативная квота запросов: выбрана для маленькой беты. Один допущенный
   запрос расходует один кредит, включая ошибки провайдера и прерывания.

Это **не токены и не деньги**. Автоматических возвратов нет: после сетевого сбоя
нельзя доказать, что провайдер не понёс расход. Администратор может отдельно
компенсировать кредит через существующий журнал. Пересмотреть перед платным запуском.

Миграция 005: максимум 50 допущенных запросов в сутки UTC на сайт, 6 в минуту
на пользователя, одна активная генерация на пользователя на 120 секунд,
положительный баланс обязателен. Проверка и списание выполняются в транзакции,
с глобальной блокировкой строки; браузеру RPC недоступны. По истечении 120 секунд
незавершённая запись перестаёт блокировать новые запросы. Запрос к провайдеру
ограничен 110 секундами, 8192 выходными токенами и размером истории.

Денежный потолок следует дополнительно установить у провайдера: количество
запросов не гарантирует фиксированный расход в валюте. В локальном dev старый
Vite proxy остаётся отдельным путём и не является защищённым сервером беты.

## Порядок развёртывания

1. Применить `202610110005_ai_request_limits.sql`, затем
   `202610110006_atomic_chat_delete.sql` через доверенный SQL Editor.
2. В Vercel добавить секрет `SUPABASE_SERVICE_ROLE_KEY` для нужного окружения.
   Не передавать его браузеру, не использовать `VITE_`, не сохранять в Git.
3. Проверить баланс существующих участников. Без кредита API вернёт 429.
4. Развернуть `supabase/functions/glow-invite`; задать `GLOW_ALLOWED_ORIGINS`
   точным списком доменов сайта и localhost. Проверить SMTP, Site URL и redirect URL.
5. Развернуть приложение после миграций. Без настройки лимитов запросы закрыты
   с 503; каталог моделей остаётся доступен после авторизации.
6. Выполнить проверки ниже, затем переводить beta на постоянный публичный URL.

Изменение общего дневного лимита выполняется оператором в SQL Editor:
`update glow_private.ai_budget set daily_requests=50 where id=true;`.
Аварийное отключение: `GLOW_AI_ENABLED=false` на сервере или `enabled=false` в таблице.

## Что исправлено в клиенте

- Повторный SIGNED_IN той же сессии не размонтирует чат.
- Запоздалая загрузка чата не заменяет более новый выбор.
- Синхронизация перепроверяет выбор и генерацию после облачных чтений.
- Повторные callbacks завершения не сохраняют ответ дважды.
- Частичный ответ сохраняется при сетевой ошибке; при ошибке сохранения
  генерация завершается, текст остаётся в памяти с предупреждением.
- Вывод принадлежит генерации независимо от текущего выбранного чата.
- Облачные widgets сохраняются одним upsert, удаление чата выполняется RPC
  в одной транзакции вместе с зависимыми данными.
- Загрузка файлов скрыта/заблокирована в облачном composer, включая Ctrl+U
  и drag-and-drop. Байты файлов пока не синхронизируются. Старые записи не удалены.

## Обязательная проверка перед приглашениями

- [ ] SQL: anon/authenticated не могут вызвать бюджетные RPC; service_role может.
- [ ] SQL: нулевой баланс, дневной потолок, параллельные запросы, лимит частоты,
      повтор ID; отклонение не списывает кредит. Два разных пользователя изолированы.
- [ ] Реальное приглашение, код из письма, имя, повторный вход и выход.
- [ ] Один аккаунт на двух устройствах: создать/изменить/удалить чат,
      сохранить состояние калькулятора/плана; чужой аккаунт не видит данные.
- [ ] GLM и Haiku через опубликованное приложение, stop/regenerate/edit.
- [ ] Потеря сети, переключение чатов и возврат вкладки во время ответа.
- [ ] Inline calculator/diagram/study plan, HTML Artifacts во всех представлениях.
- [ ] Реальный телефон: клавиатура, симметричные поля, прокрутка и кнопки.
- [ ] Постоянный URL открывается без Vercel-аккаунта, но требует входа Glow.

Остаётся нерешённым: закрытие браузера/вкладки до сохранения ответа. Буфер в памяти
не переживает закрытие; требуется серверное сохранение генерации и восстановление
её статуса. Также нет точного биллинга, полного offline-режима, приватного файлового
Storage или сквозного доказательства синхронизации. Не выдавать автотесты за эти проверки.
